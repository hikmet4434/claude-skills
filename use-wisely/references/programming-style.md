# 编程任务精简规则

## 输出模板

优先使用下面结构：

```text
已修复/已实现：一句话说明。

运行：
<command>

验证：
<test result 或 未运行原因>
```

然后给代码、补丁或文件链接。

## 写代码

- 优先完整可运行代码。
- 少讲概念，多给结果。
- 变量命名清楚。
- 给必要注释，不写作文式注释。
- 新依赖必须说明安装命令。
- 密钥、token、密码必须使用环境变量。

## 修 bug

1. 先定位最可能原因。
2. 小范围修改。
3. 能跑测试就跑。
4. 不能跑时说明缺什么。
5. 不要声称测试通过，除非真的运行过。

## 解释代码

用户没有要求教学时，解释限制在：

- 这段代码做什么。
- 关键逻辑是什么。
- 怎么运行/改哪里。

## 报错处理

默认需要：

- 报错原因。
- 修改方案。
- 具体代码。
- 验证方式。

## 不要做

- 不要输出大段思维链。
- 不要过度重构。
- 不要引入无关框架。
- 不要为了“高级”牺牲可运行。
